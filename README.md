# AI Novel Translator CLI

เครื่องมือแปลนิยายหลายบทด้วย TypeScript และ Node.js รันบนเครื่องผ่าน terminal ใช้ OpenAI แปลข้อความ พร้อมเรียนรู้ศัพท์ เก็บบริบทเรื่อง และบันทึกความคืบหน้าอัตโนมัติ ไม่ต้องติดตั้งฐานข้อมูล เว็บเซิร์ฟเวอร์ หรือ UI

ค่าเริ่มต้นแปลภาษาจีนเป็นภาษาไทย สามารถเปลี่ยนคู่ภาษาและโมเดลได้ใน `config.json`

## เริ่มใช้งาน

ต้องมี Node.js **22 ขึ้นไป**, npm และ API key ของ OpenAI ที่มีสิทธิ์ใช้โมเดลที่เลือก

```bash
npm install
```

คัดลอก `.env.example` เป็นไฟล์ชื่อเดียวกันโดยตัดส่วน `.example` ออก แล้วใส่ API key ของคุณ:

```dotenv
OPENAI_API_KEY=your_api_key
```

หรือกำหนด `OPENAI_API_KEY` ผ่าน environment ของ terminal ได้โดยตรง ค่าที่กำหนดผ่าน terminal จะมีลำดับความสำคัญสูงกว่าไฟล์ อย่า commit API key ลง Git

นำไฟล์นิยาย UTF-8 นามสกุล `.txt` ใส่ใน `raw/` แล้วรัน:

```bash
npm run translate
```

รับฉบับแปลที่ `output/` โดยใช้ชื่อไฟล์เดิม โปรแกรมไม่เขียนทับต้นฉบับใน `raw/`

โปรเจกต์มีข้อความจีนตัวอย่าง `raw/chapter-001.txt` และ `raw/chapter-002.txt` สำหรับลองใช้งาน ให้ย้ายออกก่อนแปลนิยายของคุณเอง และใช้หนึ่งโฟลเดอร์โปรเจกต์ต่อหนึ่งเรื่องเพื่อไม่ให้ glossary และบริบทปนกัน

**การแปลจริงมีค่า API** และจะส่งข้อความต้นฉบับ ศัพท์ที่เกี่ยวข้อง บริบทเรื่อง และคำแปลก่อนหน้าที่จำเป็นไปยัง OpenAI ส่วนผลแปลและสถานะทั้งหมดเก็บเป็นไฟล์ในเครื่อง โปรแกรมตั้ง `store: false` ในคำขอ API แต่ไม่ได้เปลี่ยนนโยบายการเก็บข้อมูลระดับบัญชีของผู้ให้บริการ

## คำสั่ง

| คำสั่ง | ผลลัพธ์ |
| --- | --- |
| `npm run translate` | แปลบทที่ยังไม่สมบูรณ์หรือมีข้อมูลเปลี่ยน และ resume chunk ที่ยังใช้ได้ |
| `npm run translate -- --file chapter-001.txt` | แปลเฉพาะชื่อไฟล์ใน `raw/` ไม่รับ path นอกโฟลเดอร์ |
| `npm run translate -- --force` | สร้างคำแปลใหม่ทุกบท ข้ามผลเดิม checkpoint และ translation cache |
| `npm run translate -- --file chapter-001.txt --force` | สร้างคำแปลบทที่ระบุใหม่ |
| `npm run translate -- --dry-run` | แสดงงานที่ต้องทำและเหตุผล ไม่เรียก API และไม่แก้ไฟล์ |
| `npm run translate -- --help` | แสดงตัวเลือกคำสั่ง |

ไฟล์เรียงตามชื่อแบบ natural order เช่น `chapter-2.txt` มาก่อน `chapter-10.txt` ประมวลผลทีละบทและทีละ chunk

เมื่อเปิด story context การใช้ `--file` กับบทกลางเรื่องต้องมีบทก่อนหน้าที่แปลสมบูรณ์และยังใช้ได้ เพื่อป้องกันการใช้บริบทผิดลำดับ หากบทก่อนหน้ายังไม่พร้อม ให้รันโดยไม่ระบุ `--file` ก่อน บทหลังจากไฟล์ที่เปลี่ยนจะถูกระบุว่าบริบทล้าสมัย โดยไฟล์คำแปลเก่ายังคงอยู่จนกว่าจะสร้างฉบับใหม่สำเร็จ

## ขั้นตอนการทำงาน

1. อ่าน config และ style guide แล้วตรวจไฟล์ต้นฉบับและสถานะเดิม
2. แบ่งข้อความตามบรรทัดที่มีเนื้อหา เก็บตัวคั่นบรรทัดและบรรทัดว่างไว้ตามเดิม
3. หากย่อหน้ายาวเกินงบ token จะแบ่งตามประโยคก่อน และแบ่งตาม Unicode character เมื่อจำเป็น
4. ให้ AI ค้นศัพท์สำคัญใหม่ก่อนแปล chunk แล้วรวมกับ glossary แบบมีข้อจำกัด
5. ส่งเฉพาะศัพท์ที่พบใน chunk พร้อมบริบทเรื่องแบบจำกัดขนาดและคำแปลก่อนหน้าบางส่วน
6. ตรวจ response และรหัสย่อหน้า บันทึกผลที่ผ่านลง checkpoint ทันที
7. สร้างบันทึกเรื่องแบบชั่วคราวใน checkpoint เมื่อเปิดใช้ story context
8. เมื่อครบทุก chunk และการตรวจโครงสร้างผ่าน จึงเขียน TXT ฉบับสมบูรณ์ manifest และบันทึกเรื่องถาวร

แต่ละบรรทัดที่ไม่ว่างนับเป็นหนึ่งย่อหน้า โปรแกรมรักษาตัวคั่น LF/CRLF บรรทัดว่าง และลำดับข้อความ รหัส fragment มีไว้ภายในและไม่ปรากฏใน TXT หากย่อหน้ายาวต้องแยกหลาย fragment จะนำผลแปลมาต่อกันโดยไม่เพิ่มตัวคั่นย่อหน้า

ไฟล์ว่างหรือมีแต่ whitespace จะถูกข้ามโดยไม่เรียก API และไม่สร้างคำแปล ใช้ UTF-8 เท่านั้น หากไฟล์เป็น UTF-16, GBK หรือ encoding อื่น ให้แปลงก่อนรัน

## โครงสร้างไฟล์

```text
raw/                          ต้นฉบับ TXT
output/                       ฉบับแปล TXT ที่สมบูรณ์
context/
  glossary.json               ศัพท์ที่ใช้งานจริง
  glossary.example.json       ตัวอย่างรูปแบบข้อมูล ไม่ถูกโหลดอัตโนมัติ
  glossary-history.jsonl      ประวัติการเพิ่มศัพท์ ความขัดแย้ง และการแก้คำเอง
  glossary-review.json        ข้อเสนอที่ขัดกับคำเดิม พร้อมรายชื่อบทที่พบศัพท์
  story-memory.json           บันทึกเรื่องจากบทที่ยังใช้ได้ และรายชื่อบทที่ล้าสมัย
  characters.json             ข้อมูลตัวละครที่สรุปจากบันทึกเรื่อง
  style-guide.md              แนวทางแปลที่ผู้ใช้แก้ได้
.state/
  checkpoints/                ศัพท์ที่ค้นแล้ว คำแปลราย chunk และบันทึกเรื่องชั่วคราว
  manifests/                  หลักฐานการแปลสมบูรณ์ hash และรุ่นบริบทที่ใช้
  memory/                     exact-match translation cache
  logs/                       token usage ของคำขอที่ได้รับ usage จาก API
  glossary-snapshot.json      สำเนาศัพท์สำหรับตรวจการแก้ด้วยมือ
  transaction.json            journal เฉพาะระหว่างอัปเดตหลายไฟล์
  run.lock                    ป้องกันการรันพร้อมกันในโปรเจกต์เดียว
src/
  index.ts                    จุดเริ่ม CLI และ signal handler
  config.ts                   schema และ fingerprint ของการตั้งค่า
  core/                       chunking, prompt, translation, QA และ narrative context
  glossary/                   การเรียนรู้ศัพท์และตรวจข้อขัดแย้ง
  providers/                  สัญญา AIProvider และตัวเชื่อมต่อ OpenAI
  storage/                    atomic writes, journal, checkpoints และ manifests
  utils/                      retry และบันทึก token usage
```

อย่านำ `.state/` ออกหากต้องการ resume หรือตรวจความถูกต้องของผลเดิม ไฟล์ใน `context/` และ `.state/` มีเนื้อหาจากนิยาย ควรสำรองไว้พร้อมต้นฉบับและคำแปล

## การตั้งค่า

`config.json` ตรวจด้วย Zod เมื่อเริ่มทำงาน ไม่รับชื่อ key ที่ไม่รู้จัก หากไม่มีไฟล์จะใช้ค่าเริ่มต้นในโค้ด

| ตัวเลือก | ค่าเริ่มต้น | ความหมาย |
| --- | --- | --- |
| `sourceLanguage` / `targetLanguage` | `zh` / `th` | คู่ภาษา |
| `provider` | `openai` | provider ที่ติดตั้งมาในรุ่นนี้ |
| `model` | `gpt-4.1` | model ID ที่บัญชี API ของคุณใช้ได้ |
| `translationStyle` | `literary` | แนวการเขียนส่งให้โมเดล |
| `tokenEncoding` | `o200k_base` | tokenizer; เลือก `o200k_base` หรือ `cl100k_base` ให้ตรงโมเดล |
| `chunkSizeTokens` | `1500` | งบต่อ chunk รวมข้อความและโครงสร้าง fragment โดยประมาณ |
| `contextWindowTokens` | `32768` | เพดานที่โปรแกรมยอมใช้ ไม่ใช่การประกาศ context limit จริงของโมเดล |
| `maxOutputTokens` | `8192` | พื้นที่สำรอง output ต่อคำขอ API |
| `contextMaxTokens` | `3000` | เพดานบริบทเรื่องใน prompt |
| `previousTextTokens` | `500` | คำแปลก่อนหน้าที่เก็บเพื่อความต่อเนื่องภายในบท |
| `safetyMarginTokens` | `1024` | งบเผื่อก่อนถึงเพดาน context |
| `temperature` | ไม่ส่งถ้าไม่ได้ระบุ | `config.json` ตัวอย่างตั้ง `0.2`; ลบ key นี้ถ้าโมเดลไม่รองรับ |
| `concurrency` | `1` | รองรับการทำงานตามลำดับเท่านั้น |
| `maxRetries` | `3` | จำนวน retry เพิ่มจากคำขอแรก |
| `retryBaseMs` | `1000` | เวลาตั้งต้นของ exponential backoff พร้อม jitter |
| `timeoutMs` | `120000` | timeout ต่อคำขอ รวมการอ่าน response |
| `minRequestIntervalMs` | `500` | เว้นระยะเริ่มคำขอแต่ละครั้งอย่างน้อยเท่านี้ |

โปรแกรมนับ token ของข้อความด้วย `js-tiktoken` ไม่ใช้จำนวนตัวอักษรแทน token โดยเพิ่ม overhead สำหรับข้อความและ JSON schema พร้อมเผื่อ 10% และ safety margin ยอด input จริงอาจต่างจากการประเมิน เพราะขึ้นกับโมเดลและรูปแบบคำขอ ก่อนเปลี่ยนโมเดลควรตรวจ tokenizer, context limit และ output limit ของโมเดลนั้น

ตัวเลือกเปิด/ปิดทั้งหมดมีค่าเริ่มต้นเป็น `true`:

| ตัวเลือก | ผลเมื่อปิด |
| --- | --- |
| `enableDynamicGlossary` | ไม่เพิ่มศัพท์อัตโนมัติ แต่ยังใช้ศัพท์ที่มีอยู่ |
| `enableTerminologyExtraction` | ไม่เรียก AI ค้นศัพท์ใหม่ |
| `enableStoryContext` | ไม่เรียก AI ทำ story notes และไม่ใช้ dependency ของบริบทจากบทก่อนหน้า |
| `enableTranslationMemory` | ไม่อ่านหรือเขียน exact-match translation cache |
| `enableResume` | ไม่ใช้ chunk checkpoint เดิม แต่ยังบันทึกความคืบหน้าและยังข้ามบทสมบูรณ์ที่ไม่เปลี่ยน |
| `enableQualityCheck` | ปิดเฉพาะคำเตือนเชิงภาษา; ยังบังคับตรวจ schema, IDs, ข้อความว่าง และโครงสร้าง |

แก้คำสั่งแปลเพิ่มเติมได้ที่ `context/style-guide.md` เช่น โทนเรื่อง การถอดเสียง สรรพนาม และรูปแบบบทสนทนา การเปลี่ยนไฟล์นี้ทำให้ผลเดิมต้องประมวลผลใหม่เมื่อรันครั้งถัดไป

## Glossary ที่เรียนรู้อัตโนมัติ

เริ่มต้น `context/glossary.json` เป็น `{}` เพื่อไม่ปนศัพท์ตัวอย่างกับเรื่องของคุณ AI จะค้นเฉพาะชื่อ ตัวละคร สถานที่ องค์กร วิชา อาวุธ ระดับ และแนวคิดที่สำคัญ ไม่ควรเก็บคำทั่วไปที่ต้องแปลตามบริบท

รูปแบบตัวอย่างอยู่ใน `context/glossary.example.json` แต่ไม่ถูกนำมาใช้เอง:

```json
{
  "林风": {
    "translation": "หลินเฟิง",
    "category": "character",
    "status": "auto",
    "firstSeen": "chapter-001.txt",
    "alternatives": [],
    "confidence": 0.95,
    "contextDependent": false
  }
}
```

สถานะ `auto` คือ AI เพิ่มเอง, `approved` คือผู้ใช้ยืนยัน และ `review` คือมีข้อเสนอขัดแย้งที่ตรวจภายหลังได้ ทั้งสามสถานะใช้แปลต่อได้ ไม่ต้องรออนุมัติ

เมื่อ AI เสนออีกคำสำหรับศัพท์เดิม โปรแกรมเก็บคำแนะนำและเหตุผลไว้ใน `context/glossary-review.json` พร้อมเพิ่ม `alternatives` และ history แต่คงคำแปลเดิมไว้ ไม่ให้ AI เปลี่ยนชื่อที่ตั้งแล้วเอง สถานะ `approved` และคำแปลของรายการนั้นไม่ถูกเปลี่ยนอัตโนมัติ ส่วนรายการ `auto` ที่มีข้อขัดแย้งจะเปลี่ยนเป็น `review`

คำประเภท `title`, `honorific`, `relationship` และรายการที่มี `contextDependent: true` เป็นแนวทางให้ปรับตามบริบท ไม่บังคับให้แปลทุกครั้งเหมือนกัน และไม่เตือนชื่อไม่ตรงแบบศัพท์คงที่ ระดับฝึกตนหรือยศที่เป็นชื่อเฉพาะคงที่ยังใช้คำเดิมได้โดยตั้ง `contextDependent: false` ในหมวด `rank` ส่วน `confidence` เป็นเพียงค่าที่โมเดลประเมิน ไม่ใช่ความน่าจะเป็นที่ตรวจสอบแล้ว

### แก้คำที่ต้องการควบคุมเอง

หยุดโปรแกรมก่อนแก้ `context/glossary.json` เปลี่ยน `translation` เป็นคำที่ต้องการ และตั้ง `status` เป็น `approved` แล้วรัน `--dry-run` เพื่อตรวจบทที่ได้รับผลกระทบ จากนั้นรันแปลตามปกติ หรือใช้ `--file` เพื่อทำทีละบทตามลำดับ

เมื่อรันจริง โปรแกรมจะบันทึกการแก้คำที่เคยรู้จักลง history และตรวจบทที่เคยใช้คำเดิม บทที่ไม่ได้ใช้ศัพท์นั้นจะไม่ถูกแปลซ้ำเพียงเพราะ glossary เพิ่มศัพท์ใหม่ หากเปิด story context บทหลังจากบทที่ต้องแปลใหม่อาจต้องสร้างบริบทและคำแปลใหม่ด้วยเพื่อรักษาความต่อเนื่อง ไม่มีการย้อนแก้ TXT เก่าทันทีระหว่างแก้ glossary

## Story memory กับ translation memory

**Story memory** เป็นบันทึกเรื่องและตัวละครจาก AI ใช้รักษาความต่อเนื่องข้ามบท เก็บ source evidence เป็น `explicit` หรือ `inferred` และระบุว่าเป็นข้อมูลจากโมเดล แม้ระบุ `explicit` ก็ยังไม่ใช่ข้อเท็จจริงที่มนุษย์ตรวจแล้ว รายละเอียดที่ไม่มีในต้นฉบับควรเป็นค่าว่าง

บันทึกระหว่าง chunk อยู่ใน checkpoint เท่านั้น จะกลายเป็นบันทึกบทที่สมบูรณ์เมื่อทั้งบทผ่านการตรวจ โปรแกรมประกอบบริบทจาก manifest ของบทก่อนหน้าที่ใช้ได้ จึงไม่ดึงเหตุการณ์จากอนาคตมาแปลบทต้นเรื่อง และจำกัดขนาดด้วยบทสรุปล่าสุด เหตุการณ์สำคัญ และตัวละคร ไม่ส่งทั้งนิยายซ้ำทุกคำขอ

`context/story-memory.json` และ `context/characters.json` เป็นมุมมองข้อมูลที่โปรแกรมสร้างใหม่ได้จาก manifest ไม่ใช่ไฟล์สำหรับเพิ่มข้อเท็จจริงด้วยมือ

**Translation memory** เป็น cache แบบ exact match ของคำแปลที่ตรวจโครงสร้างแล้ว key รวม source hash การตั้งค่า prompt ทั้งหมด ศัพท์ที่เกี่ยวข้อง บริบท และข้อความก่อนหน้า ประโยคสั้นเหมือนกันจึงไม่ถูกใช้ข้ามบริบทที่ต่างกัน ไม่มี vector database หรือ semantic search

## การหยุด ทำต่อ และข้อมูลล้าสมัย

กด `Ctrl+C` เพื่อหยุด แล้วรันคำสั่งเดิมเพื่อทำต่อ หากมี chunk ที่ผ่านแล้วและ fingerprint ยังตรง โปรแกรมจะไม่เรียกแปล chunk นั้นซ้ำ คำแปลสำเร็จจะถูกบันทึกก่อนเรียก API ทำ story notes ดังนั้นหากขั้นบันทึกเรื่องล้มเหลว ครั้งหน้าจะทำต่อจากส่วนนั้นได้

ผลเดิมใช้ได้เมื่อมี manifest สมบูรณ์ source hash การตั้งค่า บริบทจากบทก่อนหน้า ศัพท์ที่ใช้ และ output hash ตรงกัน การมีไฟล์ใน `output/` อย่างเดียวไม่ถือว่าแปลสำเร็จ

| สิ่งที่เปลี่ยน | การจัดการ |
| --- | --- |
| เพิ่มศัพท์ใหม่ | ไม่ย้อนแปลบทสมบูรณ์ทั้งหมด |
| แก้หรือลบคำที่บทนั้นเคยใช้ | บทนั้นต้องแปลใหม่ และบริบทปลายทางจะล้าสมัยเมื่อเปิด story context |
| แก้ต้นฉบับ | สร้าง checkpoint ใหม่ให้บทนั้น และตรวจ dependency ของบทหลัง |
| เพิ่ม/ลบ/เปลี่ยนลำดับบทก่อนหน้า | ตรวจ dependency ใหม่ ไม่ใช้บริบทเดิมโดยไม่ตรวจ |
| เปลี่ยนโมเดล คู่ภาษา style guide หรือการตั้งค่าการแปล | ยกเลิกผลเดิมตาม fingerprint |
| เปลี่ยนเวลารอ retry, timeout หรือราคาประเมิน | ไม่ยกเลิกคำแปลเดิม |
| ไฟล์ output หายหรือถูกแก้ | ไม่ถือว่ายังสมบูรณ์ อาจใช้ checkpoint ที่ยังเข้ากันได้เพื่อสร้างคืน |

ไฟล์เก่าจะอยู่จนกว่าจะได้ผลใหม่ครบทั้งบท หากการลองใหม่ล้มเหลว ฉบับสมบูรณ์เก่าไม่ถูกลบทิ้ง แต่ต้องตรวจสถานะ `pending` หรือ `staleChapters` ก่อนนำไปใช้

การเขียนใช้ไฟล์ชั่วคราวแล้ว rename พร้อม journal แบบ roll-forward เพื่อกู้การอัปเดตหลายไฟล์ที่ค้างอยู่เมื่อเริ่มครั้งถัดไป การกู้ transaction เกิดก่อนเรียก API ข้อมูลถูกออกแบบให้ทำซ้ำได้โดยไม่เพิ่ม history หรือ conflicts ซ้ำ ไม่ควรแก้ไฟล์สถานะระหว่างโปรแกรมกำลังทำงาน

ถ้า `--dry-run` พบ transaction ค้าง จะขอให้รันปกติก่อนเพื่อกู้สถานะ เพราะ dry run ไม่อนุญาตให้แก้ไฟล์ โปรแกรมป้องกันการรันสองตัวพร้อมกันด้วย PID lock และตรวจ lock ของ process ที่หยุดไปแล้ว หาก lock เสียอ่าน PID ไม่ได้ จะให้ตรวจว่าไม่มี process ทำงานอยู่ก่อนจัดการไฟล์ lock เอง

การปิดเครื่องกะทันหันหรือ filesystem เสียหายยังมีความเสี่ยง ควรสำรองไฟล์สำคัญเป็นระยะ

## การตรวจคุณภาพและข้อจำกัด

โครงสร้างที่ผิด เช่น รหัสย่อหน้าหาย ซ้ำ สลับลำดับ ข้อความว่าง response JSON ผิด schema หรือมี line break เกิน จะทำให้คำขอล้มเหลวและ retry ตามที่ตั้งไว้ ไม่บันทึกเป็นคำแปลสมบูรณ์

ข้อความสั้นผิดปกติและศัพท์คงที่ที่อาจใช้ไม่ตรงเป็น **คำเตือน** แสดงใน terminal และเก็บใน manifest ไม่แก้คำแปลเองเพราะการตรวจอาจผิด โดยเฉพาะประโยคที่ใช้สรรพนามแทนชื่อ การตรวจอัตโนมัติไม่รับประกันความถูกต้องทางความหมาย ความครบถ้วนเชิงเนื้อหา หรือคุณภาพวรรณกรรม

คำขอที่มีปัญหา network, timeout, HTTP 408, 429 และ 5xx จะ retry แบบ exponential backoff พร้อม jitter และเคารพ `Retry-After` ส่วน authentication, request ที่ไม่รองรับ และการปฏิเสธจากโมเดลจะหยุดโดยไม่ retry ไม่สิ้นสุด หาก context เกินงบจะหยุดพร้อมคำแนะนำให้ปรับขนาด

รุ่นนี้มี OpenAI provider เท่านั้น ใช้ Responses API พร้อม Structured Outputs โมเดลต้องรองรับรูปแบบนี้ หากต้องการ provider อื่น ให้ implement `AIProvider` ใน `src/providers/types.ts` และเลือกสร้าง adapter ใหม่ที่จุดเริ่ม CLI โดยไม่ต้องแก้ translation engine

อ้างอิงรูปแบบคำขอจาก [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) และ [Responses API](https://developers.openai.com/api/docs/guides/responses)

## Token usage และราคา

แสดงยอด token ที่ API รายงานในแต่ละรอบ และเก็บเฉพาะเวลา stage โมเดล และ usage ลง `.state/logs/` ไม่บันทึก API key หรือ request body หากไม่ส่ง usage กลับมาจะไม่เดายอดแทน

โปรแกรมไม่ฝังราคาของโมเดล หากต้องการประมาณค่าใช้จ่าย ให้เพิ่มราคาที่คุณตรวจสอบเองใน `config.json` เช่นรูปแบบด้านล่าง โดย **ตัวเลขนี้เป็นตัวอย่างรูปแบบ ไม่ใช่ราคาจริง**:

```json
{
  "pricing": {
    "inputPerMillion": 1,
    "outputPerMillion": 2,
    "currency": "USD"
  }
}
```

เพิ่ม `pricing` เป็นอีก key ใน config ปัจจุบัน ยอดประมาณคิดจาก token ที่ได้รับรายงานและราคาที่กรอก ไม่ใช่ใบเรียกเก็บเงินจริง และยังไม่แยกราคาของ cached input
